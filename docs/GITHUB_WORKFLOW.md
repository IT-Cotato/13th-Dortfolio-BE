# 깃허브 전략

## 브랜치 전략

GIT FLOW

- `develop`: 개발 중인 코드가 위치합니다. 새로운 기능을 병합하기 전에 이 브랜치에서 통합 및 테스트합니다.
- `feature`: 새로운 기능 개발을 위해 `develop` 브랜치에서 분기합니다. 기능 개발이 완료되면 `develop` 브랜치로 병합합니다.
- `fix`: 버그 수정을 위한 브랜치입니다.

예시:

```text
feature/#20-note-release
```

## 커밋 컨벤션

- `type: 작업 내용`


- `feat`: 새로운 기능
- `fix`: 버그 수정
- `docs`: 문서 수정
- `refactor`: 코드 리팩토링 (기능 변경 없음)


- `test`: 테스트 코드 추가 및 수정
- `build`: 빌드 파일 수정
- `ci`: CI 설정 파일 수정
- `chore`: 빌드/패키지 매니저 설정 변경
- `environment`: 개발환경 세팅

예시:

```text
feat: 노트 CRUD
```

## Issue 규칙

이슈 제목은 `Feat: member 도메인 구현` 형식으로 작성합니다.

## PR 템플릿

PR에는 관련 이슈, 작업 목적, 작업 내용, 스크린샷(선택 사항), 체크리스트를 작성합니다.

## 리뷰 전략

- 팀원 한 명이 리뷰하고 approve하거나 수정 사항 반영 후 본인이 merge합니다.
- merge 방식은 squash-and-merge를 사용합니다.
- PR을 합친 뒤에는 브랜치를 삭제하고 새로 생성해서 다음 작업을 진행합니다.

## Pull Request 규칙

- PR 제목은 작업 의도를 알 수 있게 작성합니다.
- PR 본문에 작업 내용, 관련 이슈, 테스트 여부를 작성합니다.
- PR은 최소 1명 이상의 리뷰 승인 후 merge합니다.
- 구현자는 리뷰 반영 후 해당 대화를 resolve 처리합니다.
- 충돌이 있으면 PR 작성자가 최신 `develop` 기준으로 해결합니다.
